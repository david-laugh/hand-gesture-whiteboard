## 3. 지연 구성 (p50 기준)

| 구간 | 값 | 근거 |
|---|---|---|
| 휴대폰 JPEG 인코딩 + 업로드(Tunnel) + gateway 수신 | **≈ 45 ms** | 전체 60 ms − 아래 서버 구간 (추정) |
| gateway → MQTT → vision 대기 | ≈ 0 ms | vision `queue_wait_ms` p50 0.02 ms |
| vision decode | 2.8 ms (p95 3.2) | vision `/metrics` |
| vision inference (MediaPipe) | 7.5 ms (p95 8.4) | vision `/metrics` |
| vision serialization + publish | 0.15 ms | vision `/metrics` |
| gesture 처리 | 0.04 ms (p95 0.05) | gesture `gesture_ms` |
| **촬영 → gesture 합계** | **60 ms** | gesture `lag_ms` |
| gesture → canvas, 그림판 렌더링 | 이번 측정에 없음 | §7 |

같은 서버 경로를 쓰는 정지 이미지 테스트(휴대폰과 Tunnel 없음)는 촬영 → gesture가 11 ~ 18 ms였다. 따라서 서버 구간은 15 ms 안팎이고, 실제 촬영의 나머지 약 45 ms는 휴대폰과 네트워크 구간이다. **지연을 줄이려면 서버보다 업로드 구간을 먼저 봐야 한다.**

## 4. 처리량 (FPS)

- 휴대폰 송신 설정은 20 fps(기본값)인데, 실제 처리는 **평균 15.8 fps**였다.
- 세션별로 보면 앞쪽 세션(14:23 ~ 15:03)은 16 ~ 17 fps(프레임 간격 p95 약 103 ms), 뒤쪽 세션(`eb74a8b9`, `e3af3a11`)은 19.5 ~ 19.8 fps로 설정값에 거의 도달했다.
- vision은 프레임당 약 10 ms라 이론상 90 fps 이상 처리할 수 있다. 처리 FPS를 제한하는 것은 **휴대폰 송신**이다. 송신 코드(`services/gateway/static/app.js`의 `sendFrame`)는 이전 프레임을 인코딩 중이거나(`busy`) WebSocket 버퍼가 남아 있으면(`bufferedAmount > 0`) 그 틱을 건너뛴다. 그래서 인코딩이나 업로드가 50 ms를 넘으면 FPS가 떨어진다.
- 손실: vision이 latest-wins로 버린 프레임은 1.0 %이고, MQTT 발행 실패(`publish_dropped_count`)는 0이다. 멈춤이 있던 세션(`76a465b2`, `9d81f831`, `2d9182ea`)에서 손실률이 6 ~ 10 %로 높았다. 멈춤이 끝나면서 밀린 프레임이 한꺼번에 도착해 vision이 오래된 프레임을 버렸기 때문이다.

## 5. 끊김 (멈춤) 분석

프레임 간격이 1초를 넘은 경우가 10번 있었고, 모두 3개 세션에 몰려 있다.

| 세션 | 시각 | 내용 |
|---|---|---|
| `76a465b2` | 14:36:33 | 5.3초 멈춤 1번 → 14초 뒤 새 세션 `59490c28` 시작 |
| `9d81f831` | 15:02:51 ~ 15:03:05 | 약 4.1초 간격으로 프레임이 1개씩만 도착 (4번), 지연도 각각 약 4.1초 → 2초 뒤 새 세션 `3913b862` 시작 |
| `2d9182ea` | 15:13:00 ~ 15:13:18 | 같은 패턴 5번 (지연 4.1초) → 2초 뒤 새 세션 `e3af3a11` 시작 |

- 멈춤 중에도 `frame_id`는 하나씩 정상으로 늘어났고, **도착 간격과 `lag_ms`가 둘 다 약 4.1초**였다. 프레임 하나가 촬영된 뒤 서버에 오기까지 4초가 걸렸다는 뜻이다. 그동안 송신 버퍼가 비지 않아 다음 프레임도 보내지 못했다.
- 같은 시간대에 vision `queue_wait_ms`는 정상이었고(max 52 ms), gesture 처리도 정상이었다. **원인은 서버가 아니라 휴대폰 → Cloudflare Tunnel 업로드 구간이 막힌 것**으로 판단한다.
- 세 번 모두 멈춤 직후 사용자가 촬영을 다시 시작했다(세션이 바뀜). 즉 **사용자가 체감하는 가장 큰 실시간성 문제**다.

## 6. 세션 첫 프레임 지연

실제 세션 9개 모두 첫 프레임만 지연이 컸다(p50 523 ms, 최대 988 ms). 두 번째 프레임부터는 정상 범위로 돌아왔다. 정지 이미지 테스트 세션도 첫 프레임이 270 ~ 550 ms였다.

- 추정 원인: 휴대폰 시계 보정값(`offset`)이 0으로 시작하고, 첫 ping 응답을 받은 뒤에 맞춰진다(`app.js`). 그래서 첫 프레임 몇 개는 휴대폰과 서버의 시계 차이가 지연에 그대로 더해진다. 실제 지연이 아니라 **측정 오차일 가능성이 크다.** 연결 직후 첫 업로드 비용이 일부 섞였을 수도 있다.
- 위 통계(§2)는 첫 프레임을 뺀 값이다.

## 7. 한계

- **canvas 구간과 그림판 렌더링 시간이 없다.** gesture → canvas 지연과 `canvas_ms`는 dashboard에만 있는데, dashboard 기록은 5분 보관이라 이미 지워졌다. 따라서 이 보고서의 "촬영 → gesture" 값은 진짜 end-to-end보다 canvas 처리 + MQTT 1회 + 브라우저 렌더링만큼 작다.
- 휴대폰 시계는 ping 왕복의 절반 정도 오차가 있다. 업로드 구간 ≈ 45 ms는 차이로 구한 추정값이다.
- 휴대폰 1대, 네트워크 1곳, 약 7.7분 분량이다. 해상도·화질 설정별 비교(`benchmark-plan.md` B3·B4)는 하지 않았다.
- CPU와 메모리는 측정하지 않았다(측정 시점에는 트래픽이 끝나 있었음).

## 8. 개선 제안

1. **업로드 멈춤 감지:** 휴대폰 페이지에서 `bufferedAmount`가 1초 이상 남아 있으면 사용자에게 "네트워크 지연"을 표시한다. 오래된 프레임이 쌓이지 않도록 버린 프레임 수도 같이 표시한다.
2. **업로드 비용 줄이기:** 해상도나 JPEG 화질을 낮췄을 때 업로드 구간(약 45 ms)과 FPS가 얼마나 좋아지는지 B3·B4 시나리오로 비교한다. 같은 Wi-Fi에서 Tunnel 없이 직접 연결했을 때와도 비교한다.
3. **첫 프레임 오차 없애기:** 첫 ping 응답(`offset` 보정)을 받은 뒤에 프레임 송신을 시작한다.
4. **측정 기록 보존:** 다음 측정부터는 dashboard `GET /api/snapshot?window_s=300`을 촬영 중 주기적으로 파일로 저장해 canvas 구간까지 포함한 end-to-end 값을 남긴다.

## 부록: 재현 방법

```bash
# 프레임별 데이터 (수신 시각 포함)
docker logs -t hgw-gesture > gesture.log
# vision 내부 처리 시간, gateway 카운터
docker compose -f compose.yaml -f services/vision/e2e/compose.e2e.yaml exec vision \
  python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8001/metrics').read().decode())"
curl http://127.0.0.1:8010/api/metrics
```

gesture 로그의 `"source": "mqtt"` 줄을 `session_id`로 묶고, `replay-*` 세션과 정지 이미지 세션(녹화 파일의 손끝 좌표가 거의 바뀌지 않는 세션)을 뺀 뒤 `lag_ms` 백분위(nearest-rank), 수신 시각 간격, `frame_id` 누락을 계산했다.
